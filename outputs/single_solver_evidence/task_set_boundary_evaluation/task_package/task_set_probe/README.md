# Task Balance GN：任务集可行性覆盖检查（本地开发）

## 本次实际做了什么

没有更改任何算法目标、权重或求解核心，没有推送代码或运行原服务器实验。
使用用户提供的 `task_balance_completion_package.zip` 的原型和本地 Panda 运动学，
检查了原“精确 FK 目标”之外、但仍满足原任务验收定义的一类输入。

代码核对来源为 `8e4aa63975d465f3de8a1eef2f7773889252c91d`：
`run_task_balance_completion.py::inputs` 调用原 `data.py::points`，该函数以
`pose=kin.forward(reference)` 生成可行点。它保证目标中心有零残差参考，
没有系统测试“任务容差区域非空，但目标中心不一定在单帧可达像集内”的情况。
这不使旧结果无效，也不证明新方法只因这个遗漏才没有显示总体增量。

## 几何构造

先产生实际上一配置 q_previous 和满足相同单帧位移边界的 q_witness。
以 q_witness 的 FK 为中心，按独立的三维单位方向 u_p、u_R 构造

p_target = FK_p(q_witness) + alpha * epsilon_p * u_p
R_target = Exp(alpha * epsilon_R * u_R) * FK_R(q_witness)

alpha 固定为 {0, 0.5, 0.95}。每个基准状态在三个 alpha 上使用相同方向。
因此 q_witness 对三个目标都通过原有数值形式的验收。
这仅证明任务集可行，不证明精确中心无解。

所有目标在比较前保存，所有 witness 先以独立齐次变换 FK 检查。
在线方法仅接收 previous、当前 target 和 dt，不能读取 witness。

### 顺序开发记录，完整保留

1. 首批 120 个 anchor 使用类似原采样的位移幅度，三个 alpha、三种方法全成功。
2. 观察首批结果后，另定一批近位移边界压力输入：参考位移各关节取
   `0.999 * velocity * dt` 随机正负号，然后只作物理限位裁剪。
   这不等于实际每个关节都用满99.9%的公共边界，因为公共边界还包含 epsilon_v，
   物理限位裁剪也可能减小位移。第二批的三个 alpha 和全部120个 anchor 在求解前固定。

第二批是**定向、极限附近的开发压力测试**，不是现场分布或普遍性证明。
没有按求解器失败筛选输入。两个阶段都是已观察开发数据，不能再标成独立测试。

## 实测结果

每格是一次运行的合格输入数/120；三个 alpha 共享同一批 anchor，不是独立复制。

| 负载 | alpha | 原GN kappa1 | 同缓存紧精度 | 相对进展0.25 |
|---|---:|---:|---:|---:|
| 常规参考位移 | 0 | 120 | 120 | 120 |
| 常规参考位移 | 0.5 | 120 | 120 | 120 |
| 常规参考位移 | 0.95 | 120 | 120 | 120 |
| 接近位移边界 | 0 | 120 | 120 | 120 |
| 接近位移边界 | 0.5 | 120 | 120 | 120 |
| 接近位移边界 | 0.95 | 114 | 120 | 120 |

近边界alpha=0.95的平均本地外层时间：
- 原GN：0.409557 ms
- 同缓存紧精度：0.889062 ms
- 相对进展：0.446571 ms

只有这一压力格出现六个恢复，不能只展示它而删除前五格。
相对进展比原GN在该格仍约慢9.0%；对紧精度约少49.8%。
这里使用本地预热的Numba运动学及箱QP、单遍；不是原服务器时延。
所有返回配置均使用独立齐次变换FK检验。原项目verifier还需复核。

## 文件

- `run_probe.py`：第一批生成与测量。
- `run_boundary_probe.py`：第二批生成与测量。

复现应复制到空输出工作目录，不能覆盖现有 measured/ 或 boundary_measured/。
依赖NumPy、SciPy及可选Numba；环境不一致会改变时间而非自动保证输出逐位相同。
本包没有声称改出了新的算法或完成了论文；它检查的是已有算法的适用输入范围。
